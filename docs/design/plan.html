First frame first.

a review player for vfx and install content: opens a clip before you have let go of the mouse, steps one true frame at a time, shows true pixels, and tells you exactly what the file is. this page is the proposed interface, engine and build order, after three hostile reviews and your first round of notes. what is settled and what is still open is in section 10.

05

The engine

rust. one small renderer per system, ffmpeg for demux and most decoding, and our own code for hap. the first build is a set of pass or fail gates, because two claims carry the whole design and neither is proven: a decoder's frame reaching the screen with no copy, and a cold start you do not notice.

frames wider or taller than the gpu's limit (16384 on most cards) are refused with that reason. hap in an .avi needs our own tag mapping; ffmpeg has none.

how the first frame gets there

  • the first thing the process does is look for a running window and hand it the file. that path loads neither the gpu nor ffmpeg.
  • otherwise the window appears at once, black. the gpu starts on its own thread while the file is opened and its first frame decoded.
  • the frame index, an exact count for mkv, the controls and audio all come after the picture.
  • rendering has its own thread, so dragging or resizing the window never freezes the video.

what "exact" means, stage by stage

  • decoded planes are the truth. the pixel readout and screenshots come from them, never from the screen.
  • scaling. at 100% and above luma is read by integer address: no filter. 4:2:0 and 4:2:2 chroma has to be upsampled; bilinear at the file's stated siting by default, nearest on request, and the panel says which.
  • color. v1 does no color management. yuv is converted by the file's tags, or by the assumption shown, and the rgb values go to the display unchanged.
  • depth. 10-bit output where the display takes it. a deeper file on an 8-bit display is dithered, with a toggle and a chip.
  • alpha. rgb is shown as stored, over black. nothing is premultiplied or divided for you.
  • float and hdr. linear exr is shown through an srgb curve, hdr is tone-mapped, and both carry a chip saying so. true hdr output is a later phase.

timing

  • silent clips, which is most install content: every frame is shown for a whole number of display refreshes. nothing is dropped. a rate that does not divide the refresh (24 on 60) gets an uneven cadence, named in the panel.
  • clips with sound: audio is the clock. on a mismatch such as 59.94 on a 60 Hz display, one frame repeats about every 17 s and the panel counts it (fig. 07).
  • locking audio to the display instead removes that repeat. it is a later improvement, not v1.

reverse, shuttle and reload

  • reverse and shuttle. hap, prores, notchlc and sequences play backward as easily as forward. h.264 and hevc play backward through the kept frames, one group at a time, and may pause between groups. audio is off.
  • reload. files are opened shared, so a render can overwrite a clip that is open. the player watches the open file's size and modified time, reloads when they change, keeps your place, and says so (fig. 22). a file still growing is left alone until it stops.

wgpu, and why it is out. the stack research recommended wgpu, on condition of a cold-start test: one layer for three systems. the engineering review then showed it offers only an unsafe, per-backend way to take a decoder's surface, and none to report when a frame reached the screen, so the hard parts would be per-system code either way. the two disagreed and i sided with the review. the cost of going native is two egui painters we write ourselves, for direct3d 11 and metal; dear imgui ships both ready-made.

also ruled out. libmpv: no exact frame number, stepping back re-decodes the whole group, and it cannot hand bc blocks to the gpu. qt: size and start time. sdl's gpu layer: cannot take a decoder's surface. libplacebo: no metal, no bc formats.

the c++ alternative is sdl3, dear imgui and the same three renderers. equal in capability and with more prior art. rust is the pick because the org's native code is already rust on the same os crates, one cargo build covers three systems, and the code that parses untrusted files is memory-safe.

the tests use a different referee per codec. hap: the blocks after snappy against the reference decoder's. h.264 and hevc: decoded planes against ffmpeg in software, which the standard makes bit-exact. prores on videotoolbox: a tolerance, since its maths is allowed to differ. counts and rates: clips generated with a known frame count and a burned-in counter, never ffprobe. the display: a known ramp read back on each gpu vendor.

timebar preview: performant, as a hybrid

  • the open clip gets a denser strip, one frame per two seconds, at most 100. the nearest of those shows at once.
  • hap, prores, notchlc and sequences: a spare decoder then replaces it with the exact frame. newest request wins. target 16 to 50 ms from local disk, to be measured.
  • h.264 and hevc: the nearest key frame only. an exact frame there can cost a whole group of decodes.
  • fallback if the measurements say no: the strip frame alone.

network volumes are look-only

  • the browser uses the folder listing and nothing else. it opens no file until you open one, read one, or ask for previews (fig. 29). a plain metadata call opens the file on windows, so that is avoided too.
  • until gate 0 has measured it, any open is assumed to change ctime.
  • cloud placeholders (onedrive, dropbox, icloud files not on disk) are treated the same way, since reading one downloads it.
  • unknown volume types count as network.
  • a test browses a share with audit logging on and fails if the server logs a single open.

cache lives in %LOCALAPPDATA%, ~/Library/Caches or $XDG_CACHE_HOME, in its own eyepiece folder. one cache file per video: its facts, its poster, its previews. no database. eviction removes only cache files this app wrote, one at a time. it never removes a directory, never recurses, and refuses to run if its folder resolves to nothing, a drive root or a home folder.

What the reviews broke

three reviewers were given the first draft and told to make it fail: one against your brief line by line, one as a video engineer, one as a vfx reviewer and an installer on site. these are the hits that changed the plan.

the attackwhat changed
the spike measured disk and decoder speed, which are the same under any graphics stack. it could not decide anything.phase 0 is six pass or fail gates on the things that do differ, on windows and macos.
wgpu offers only an unsafe, per-backend way to import a decoder's surface, and none to read present timing. you would write three native integrations anyway.wgpu is out, against the stack research's conditional recommendation. one small native renderer per system (section 10).
250 ms ignores what dominates: driver load after a reboot, a mov with its index at the end on a sleeping nas, counting frames in an mkv.targets carry their conditions. the instance check runs before anything loads. the index builds in the background. no number is promised over a network.
one enter on a nas folder opens 300 files to size the window.enter opens the selected card only. play folder on a network path asks once, with the count.
"look-only" would still open files: rust's file metadata call opens the file on windows.network paths use listing data only, and a test fails the build if the server logs an open.
loop analysis has two hard cuts per cycle and only one is the seam. with audio the other one clicks.the trip back is a short hold on black with audio faded. audio plays sample-exact through the seam.
every pointer move and every key brought the controls up over the pixels being inspected.keys never show them. once zoomed, only the top and bottom edges do. a pinned panel stands alone.
a ribbon gives a 216-pixel-high window; the menus do not fit. a totem is narrower than the control row.640 × 360 minimum with the clip letterboxed, and a row that shortens in a stated order (figs 15, 16).
speed was invisible with the controls hidden, and leaked between tabs. play folder with loop "one" looped clip one forever.a chip whenever speed is not 1×. speed and loop belong to the tab; a folder starts on loop all.
comparing v011 and v012 meant finding the frame again on every flip.two clips of the same size and length share frame, zoom and pan when you switch.
frame hashes against ffmpeg are the wrong referee for half the codecs.a referee per codec (section 05).
a 250-frame group at 4K is 6 GB. the ring of decoded frames cannot hold it.one refresh is promised only inside the kept frames. the group length is shown. long-group timebar previews use key frames.
amber on every hap file teaches people to ignore amber.amber only for a fault in this file. what a format cannot say is gray.
the hover previews would read 10 GB to thumbnail one folder of hap.posters only up front. the 24 preview frames are made on first hover.
nothing teaches the keys. volume was only a mute button. the launch screen was not column view.right-click and ? (fig. 21), a level slider, and columns from the first screen (fig. 27).
