# developing eyepiece

what a contributor needs and a user does not: how the code is laid out, how to build, run and test it, what has been measured and where, what is known to be missing, the mac port, the icon, packaging and signing, and the phase 0 gates. what the player does for its user is in the [readme](../README.md).

the approved design is `docs/design/plan.html` (open it in a browser); settings, help, about and updates are designed in `docs/design/settings.html`. decisions that are hard to reverse are in `docs/adr/`, one file each, and the project's words in `GLOSSARY.md`. the rules the code cannot show: media is read-only, network volumes are look-only, the cache's guards, no number without a measurement, and every metadata value exact or labeled.

**where numbers come from.** every number here was measured, and says when. windows numbers are from the windows dev machine (a 10-core, 20-thread cpu, a 60 Hz display) unless said otherwise; mac numbers are from the mac build machine (an m2 macbook air, macOS 26.6, 60 Hz).

## status

phase 1, in progress, on windows; then macos. it plays hap, notchlc, prores, h.264, hevc and vp9, from mov, mp4 (fragmented too), mkv and webm, and stills (png, jpeg, tiff, tga, dpx, exr: one file, or a numbered run of them as one clip). settings, help, about and the update check are designed (`docs/design/settings.html`, approved 2026-11-24) and being built.

the window has no title bar: the controls are drawn by the player to the approved design, and come up when the pointer moves. on windows 11 a line one pixel wide runs round it, black, drawn by the system outside the picture: with no line asked for, the system left that pixel bare on three sides, and a window behind showed through it (seen 2026-11-24). that the black line ends it is reasoned from the window's measures, not seen on a screen.

folders are listed off the drawing thread, each on its own, so a slow share holds up only its own column. the sidebar's places and volumes, with each local disk's label, are still read on the drawing thread, once, when the browser first comes up; the pinned folders come in from a thread of their own. on a network volume nothing but the listing is read until a file is opened, its metadata is asked for, or the folder's previews are asked for with the button on its note, which says how many files they read.

### the look, against the design

the look follows `docs/design/plan.html`: its colors, measurements, icons and type (ibm plex mono and archivo, in `assets/fonts` with their licenses). letters the two lack, as in a folder named in polish, greek or russian, are written in the system's own ui face, read from the system's fonts as the player starts; a name in a script that face lacks too still shows empty boxes. type follows one rule (2026-11-24): ibm plex mono only for titles and numbers (headings, values, file names and paths, key caps), archivo for every sentence, note, message, tooltip, button and menu word, a sentence with numbers in it included.

checked by putting the window's own pixels beside the design's mock at the same scale. not yet looked at by a person on a real screen: the shadow, resizing from the edges, snapping, and display scales other than 100%.

### where the build differs from the design

- the bar's row of controls sits in the middle of the bar (between its top line and the timebar), and every line of text is centered by its figures and capitals, not by its line's box: two corrections made on first seeing the design in the player.
- a plain click on the picture plays or pauses (2026-11-24), in place of the design's show and hide. a double click fills the display and leaves play and the frame as it found them: its first click plays or pauses as any click does, and its second takes that back. the design had a double click go between fit and the last zoom; it was changed after use.
- `-` and `=` zoom, and speed takes shift with them.
- the browser's "play folder" is named "open folder", and stands at the right end of the address beside the view choice, where the metadata column no longer pushes it aside.
- a card's "new tab" action is gone; the actions are open (or "open selected"), and reveal for a local file or read metadata for one that is look-only.
- on macOS the window's buttons are the system's own, not drawn by the player (see [macOS](#macos)).
- a file opens playing (`play_on_open = on`, 2026-11-24), where figs 02 to 26 have it open paused on its first frame.
- markup does more than the plan's "kept small" list (the owner's asks, 2026-11-25): shift draws a square or a round circle, and a pen's line is smoothed, with a slider for it on settings' screenshots page, which the settings design does not have.

## build, run and test (windows)

needs rust (stable, msvc target) and the visual studio c++ build tools. the tests need a gpu with a video decoder: one unit test and the end-to-end test check hardware decoding, and fail on a machine without it.

```powershell
# once: fetches the pinned lgpl ffmpeg and a libclang into third_party (ignored by git)
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\setup.ps1
cargo test
cargo run --release -- wall_v012.mov
# end to end: drives the built program (target\release) with real keys and checks what it says (a window opens for a few seconds)
powershell -NoProfile -ExecutionPolicy Bypass -File tests\e2e.ps1
# dragging the window by its picture, with the real mouse (it borrows the pointer for a few seconds: hands off)
powershell -NoProfile -ExecutionPolicy Bypass -File tests\drag.ps1
# pacing on real clips of your own: plays each for 10 s; fails a clip that did not open, lost frames, or ran late
powershell -NoProfile -ExecutionPolicy Bypass -Command "& tests\play.ps1 -Clips a.mov,b.mov"
# measurements on clips of your own: start to first picture, and what stepping back costs
powershell -NoProfile -ExecutionPolicy Bypass -Command "& tests\launch.ps1 -Clips a.mov,b.mp4"
powershell -NoProfile -ExecutionPolicy Bypass -File tests\backstep.ps1 -Clip a.mp4 -Frames 600 -KeyEvery 60
# the timebar's picture on clips of your own: pointer to the first picture, and to the one that replaces it
powershell -NoProfile -ExecutionPolicy Bypass -Command "& tests\hover.ps1 -Clips a.mov,b.mp4"
# the unit tests on a mac, from git bash on the windows machine: sends the working tree over ssh and runs them there
sh scripts/mac-test.sh <user>@<host>
```

`scripts/mac-test.sh` keeps the mac's copy in `~/src/eyepiece-player` and needs rust, apple's command line tools and the ffmpeg that `spike/mac/setup.sh` built (in `~/src/eyepiece/spike/third_party/ffmpeg`). it builds niced, on half the cores, refuses to build with under 4 GB free, and works with the screen locked: the unit tests draw into pictures with no window.

### how the tests drive the player

the tests drive the controls with posted messages, not the real pointer and keyboard. `EYEPIECE_POSTED_POINTER=1` tells the player so: it then listens only to pointer messages carrying the tests' mark (0x8000 in the first parameter) and to keys with no scan code, and takes what is held with a posted key from the message's own low bits (1 shift, 2 alt, 4 control); shift and control alone, going down or up, say what is held after them the same way. a person using the machine during a test run does not disturb it, nor it them. where only the picture can tell (a tooltip, the table of keys), the test asks the window for its own picture (`PrintWindow`), never the screen.

`tests\e2e.ps1` also points `APPDATA` at a folder of its own, so it starts from the defaults and leaves your settings alone, and names a folder of its own with `EYEPIECE_CACHE` to stand for the os cache folder, so the pictures it makes stay out of your cache (`%LOCALAPPDATA%\eyepiece\cache\previews`). and it sets `EYEPIECE_INSTANCE` to a name of its own: players started with the same name hand files only to each other, so the tests can check the hand-over without ever reaching a player of yours. the test scripts set `play_on_open = off`, since their checks expect the first frame; one check runs on the default, which plays a file as it opens. dropping a file on the window is not covered by the end-to-end test.

the window's title, which the taskbar shows and the tests read, is `name · frame / count · size · codec, how it is decoded · rate`, then whatever is not as a clip opens (looping off, loop analysis, speed, the look, the guides, the zoom and the pixel under the pointer, the marks on the frame, markup mode, the browser over it); it is left alone while a clip plays. it also says what went wrong: ` · n late` (refreshes that went by without the frame that was due), ` · n could not be shown` (frames the file could not give), and ` · reading` while the frame it names is still on its way. a tab with no clip is titled `eyepiece`, and one whose file did not open `eyepiece · why`.

### the timing checks

the timing checks (`play.ps1`, `launch.ps1`, `backstep.ps1`, `hover.ps1`) mean nothing on a busy machine, and a busy gpu counts: on 2026-11-23, with an encoder and two other programs on the gpu, a hap clip that had run with 2 late refreshes in 4 s showed 53; the same day, with other test suites holding the machine at 97% cpu, a clip that had run with 2 late refreshes in 10 s showed 246 in 6 s, with the same build.

## measurements and known gaps

### playback

what has been played on real files, at 4K and 60 frames a second:

- hap, hap alpha, hap q, hap r and hap hdr, and hap q at 8K: our own code, blocks to the gpu as stored. hap q alpha and alpha-only follow the published spec, but no file of either was at hand. hap hdr goes to the screen as stored: values above 1.0 clip, with no tone map and no chip saying so yet.
- h.264 and 10-bit hevc: the system's hardware decoder, drawn from the decoder's own surface with no copy. when the gpu does not take a stream (10-bit h.264, 4:2:2 on most cards) the same clip decodes in software.
- prores 422 hq: ffmpeg in software, one frame at a time on every core. prores 4444 xq at 4K60 does not hold its rate in software on the dev machine (about 30 frames a second), as phase 0 measured.

standing still, the player reads ahead what play would show next (one frame for a lane with one worker's worth, up to 32 for stills and notchlc), so play starts on frames that are already there.

known gaps:

- **notchlc plays at speed, but a lone frame takes one core's whole decode.** ffmpeg decodes a notchlc frame on one core, so the player decodes up to eight at once, each worker with its own decoder, and keeps what it decoded in up to a quarter of ram. a 4K60 notchlc clip, as a benchmark of the reader alone on the dev machine while busy: 119 of 120 frames on time in the first pass, all in the second (medians of five, `plays_at_speed` in src/media/clip.rs); a frame not ready when stepped to took 113 ms. in the player itself, 4 s of play from a standing start (about 240 refreshes): 56 late refreshes before frames were read ahead while standing still (2026-11-23), and 3, 1 and 1 with the read-ahead (2026-11-24, three runs, cpu at 0 to 2% and the gpu at 2% before each). in the same three runs hap q 4K60 had 1, 1 and 1 late, hevc 10-bit 4K60 0, 0 and 1, and prores 422 hq 4K60 1, 0 and 1. an earlier batch that day, with the gpu at 17%, read 17, 2, 2 and 11. values read as 12-bit.
- **4K sequences play at speed in the reader's benchmark, and from ram after the first pass while they fit in a quarter of it; in the window they are not measured yet.** frames decode on up to eight workers at once and stay in memory up to a quarter of ram, least recently wanted out first. 48-frame 4K sequences at 24 a second, dev machine busy, files read from the os cache: exr half zip, 10-bit dpx, 8-bit png and tga had 47 of 48 frames on time in the first pass and 48 in the second (medians of five, `plays_at_speed`). a frame not ready when stepped to takes one whole decode: 64 ms (tga) to 229 ms (png). a sequence longer than a quarter of ram decodes again every pass. reading from a disk or a network share, 16-bit png and the upload of 133 MB float frames to the gpu are not measured. exr values above 1.0 stop at white (no tone map), exr compressions other than none, rle and zip are untested, and the rate of a sequence cannot be typed in yet. for exr the pixel readout gives what the screen is sent, on a 16-bit scale, not the file's own numbers.
- **prores 4444 xq at 4K60 does not play at speed.** ten seconds of play in the installed build, late refreshes of about 600 (2026-11-24, `tests\play.ps1`, one run, with another program on the gpu at 15 to 23%): hap q 1 and 1 (two clips), h.264 2, prores 422 hq 2, notchlc 11, prores 4444 xq 225: ffmpeg decodes it in software, and this cpu (10 cores, 20 threads) does not have 60 a second of it: ffmpeg's own program (9.0.1, the one on the dev machine's path; the player links 9.0.2) decodes the clip (3.9 Gbit/s, apple's rate for the format at this size) at 4 frames a second on one thread, 47 with every core on the slices of one frame, as the player has it, and 42 with a frame to a thread; the player's reader alone gets 41 (64 of 120 frames on time, `plays_at_speed`). with that decoder 60 is not there on this cpu. 10-bit hevc had 14 at 59.94 and 11 at 60 in that run, and that was the timebar strip's reader, put right since: it let its decoder go 5 s after the strip was made, in the middle of play, and the picture waited on it. the 60 fps clip, three runs of each build in turn in one sitting: 3 s of play begun 4 s after the clip opened lost 13, 7 and 9 refreshes before and 1, 1 and 3 after; 10 s begun 1 s after it opened lost 9, 5 and 6 before and 3, 3 and 4 after, where a build from before there was a strip lost 5, 2 and 3. installed, later in that sitting: 6, 5 and 6 for the 3 s, and 1, 1 and 2 for the 10 s; and the eight clips again, ten seconds each, with the gpu at 34% before: hap q 2 and 1, h.264 1, hevc 1 at 59.94 and 3 at 60, prores 422 hq 2, prores 4444 xq 194, notchlc 3 (the player held 8.2 GB by the end of it, 438 MB for prores 422 hq, 153 to 273 MB for the hardware ones and hap). play begun after some seconds stood still loses a few refreshes at its start whatever the strip does (a build that asked for no strip, begun 8 s after the clip opened, lost 10, 10 and 3 in 3 s; begun after 1 s, 2, 1 and 2): not looked into, and it may be the test's doing, whose window is on top but is not the active one. starts in the same sitting (`tests\launch.ps1`, medians of six): hap q 248 ms, prores 422 hq 242, h.264 274, hevc 296.
- prores decodes in software only on windows, with ffmpeg's decoder. prores 4444's alpha is drawn from its own plane, as the file stores it (whether the color is already multiplied by it, the file does not say and the player does not ask): the alpha channel's view shows it and a saved frame keeps it. tested on a 64-pixel clip with a ramp of alpha, on both renderers; not tried on a file from another tool.

### start

- **a cold start is near the 250 ms target: under it for hap and prores, over it for h.264 and hevc.** from the process starting to the first picture, on the dev machine, 4K clips, 2026-11-24, with the graphics device now made on a thread of its own from the first moment (it is 160 ms of the start, the driver loading, and needs no window): hap q 203 ms and h.264 269 ms (medians of twelve launches on a quiet machine; the build before, launched in the same sitting, 267 and 316 ms); prores 239 ms and hevc 279 ms (medians of six, 287 and 341 ms before). numbers from different sittings do not compare: the same build read 231 ms for hap q in the morning and 267 ms later that day. where the rest goes, by stage timers that are not in the program: about 19 ms before the program's own code runs (the system loading it and ffmpeg's libraries), 5 to 20 ms to read the file's header, 21 ms to make the window, then the wait for the device, 8 ms for its link to the window, and for h.264 and hevc 60 ms to make the hardware decoder and decode the first frame, which cannot start before the device is there. loading ffmpeg's libraries at first use, which the plan asks for so that a second launch never loads them, is not done: the linker cannot delay libraries whose import files were made by another toolchain, as the bundled ones are. `tests\launch.ps1` measures the whole.
- the installed folder is 113 MB against a 60 MB target: ffmpeg's decoder library is 100 MB of it, built with every decoder there is. a build with only ours is later work.

### stepping back and playing backward

- **stepping back in h.264, hevc and vp9 is instant only inside the frames kept.** the player keeps the frames it last decoded, as many as fit in 512 MB (about 20 at 4K, 32 at most), and a step back inside them is one or two refreshes. the step that leaves them decodes again from the key frame before: on the dev machine that one step took 34 and 101 ms in two runs on 4K hevc with a key frame every 60 (2026-11-24), and 1.66 s on 4K h.264 with a key frame every 250, from the middle of its group. until that day a jump in a clip whose frames are stored out of the order they are shown in (most h.264 and hevc) decoded the group before its own as well, because ffmpeg's mov reader goes back a key frame when asked for a key frame's own decode time: the same step took 329 and 396 ms in the same sitting, and a jump to the middle of a group 237 and 312 ms against 106 and 118 ms now. a test counts the pictures decoded on the way to a frame. `tests\backstep.ps1` measures it on a clip of your own. hap and prores frames stand alone and are not affected. a jump straight onto a key frame of hevc with open groups (x265's default) decodes the whole group before it too: asked for a time before that key frame is shown, which is where the player asks from, ffmpeg's reader of mov and mp4 goes back to the key frame before (seen on the test clip `hevc_open_320.mp4`, not measured at 4K). the timebar's reader asks from inside the key frame's group instead.
- playing backward (J) in h.264, hevc and vp9 runs in bursts: frames are decoded forward from a key frame and only the last ones are kept, so every 20 frames or so at 4K it stops to decode again. hap and prores play backward evenly.

### the timebar's picture

the design's hybrid (fig. 04, plan section 06): with the pointer on the timebar, a small picture stands over the number of the frame under it, at once: the nearest picture had. once a clip's first frame is up, a second reader of the clip (so the picture on screen does not move) makes the clip's timebar strip: a frame every two seconds, at most 100 spread over a longer clip, each at most 320 × 180 (twice the design's box, as its prototype draws it, so a picture of it is as sharp as what replaces it at 200%), coarse first as a card's previews are, one frame at a time behind anything else asked of that reader, and none while a clip plays. then the reader reads the frame under the pointer, or for h.264, hevc and vp9 with key frames apart the key frame nearest it, so no picture costs a decode of a whole group; a picture had already is not read again, and while frames are asked for faster than they can be read only the newest is. the box is fig. 04's (its line, the picture three in from it, the number in the 20 under it, checked against the figure at 100%), and the picture is drawn at full brightness: it was dim while it was not of the frame named, which with key frames apart it now never is. while such a clip plays nothing is read for the timebar, and the timebar strip's nearest picture shows (before it there was none). a clip of one frame gets no timebar strip. on a network volume no timebar strip is made, since the user's opening a file there does not license reading it again and again (adr 0004): the picture comes when the frame under the pointer has been read, as before, and a timebar strip asked for there opens nothing (`nothing_more_is_read_on_a_network_volume`).

measured on the dev machine on 2026-11-24, release build, cpu at 2 to 9% and the gpu at 2 to 6% before each: at the reader alone (`the_timebar_pictures_are_timed` in src/win/pictures.rs), a 4K hap q frame under the pointer took 8 to 23 ms (66 and 94 ms the first time, which opens the clip), a key frame of 4K h.264 with a key frame every 250 took 30 and 64 ms (126 ms the first) and with one every 60 17 to 27 ms; a timebar strip of 100 from a 200 s 4K clip took 17.3 MB and 0.9 s to make (hap q) or 1.6 s (h.264, a key frame every two seconds), and the 3 and 10 s spike clips' timebar strips of 2 and 3 took 17 and 32 ms. in the window (`tests\hover.ps1`, which reads the window's own picture, each look taking 35 ms), the first picture was up 22 to 83 ms after the pointer came onto the timebar, and a 4K hap q frame under it replaced that 115 to 181 ms after (four runs of 6 hovers, with the gpu at 2 to 6% before them; in 4 of each 6 the script saw the change, in the others it was too small to see): not the design's target of 16 to 50 ms. timestamps put into the program for one run (not kept) put the read at 28 to 50 ms there (it shares the gpu with the window) and its answer reaching the window 15 to 28 ms later. in the h.264 clips the key frame nearest every hover was in the timebar strip, so the first picture was the last.

while the reader holds a clip (from the timebar strip's first picture to 5 s after the last one asked of it), the player's working set was at most 156 MB on the 200 s hap q clip and 181 MB on the h.264 one, against 101 and 115 MB for the same clips opened through a share the dev machine serves to itself, where no timebar strip is made; on the gpu, 40 MB against 23 for hap q, and 1165 MB against 585 for h.264, whose second hardware decoder keeps 4K surfaces for frames it might be asked for again, back to 605 MB once the reader lets the clip go (two runs each). a hundred 4K pictures held 760 MB of the gpu's until the reader's device, which never presents, was made to hand back what it let go. the window is not woken for each picture of the timebar strip, and draws again for one only while the timebar is hovered: before that, steps right after a 200 s 4K clip opened took 26 to 27 ms while its strip was made, against 2 to 3 ms without it, and flips between two tabs (] and [) of 4K hap q 25 to 32 ms against 2. now steps take 2 to 3 ms either way in hap q and h.264, and flips of hap q 3 ms (medians of 15 steps and 12 flips, two runs of each build in turn, cpu at 3 to 5%); flips of 4K h.264 took 2 to 3 ms either way all along. the timebar strips of prores, notchlc and sequences are not timed: a long 4K exr sequence's, a full decode a frame, is likely the costliest. a file whose data is not on the disk (a cloud placeholder) gets a timebar strip like any local file once it is opened: the browser's test for that is not offered to the rest of the player yet, and no real placeholder has been tried.

known gap:

- **the timebar strip makes way only for play.** it starts once the clip's first frame is up, waits while a clip plays and lets every hover and loop analysis's question go first, but the frame a step lands on and the frames read ahead are read beside it, on their own threads, not before it: the design's one queue of reads per volume (fig. 30) is not built. in the window the frame under the pointer comes 103 to 173 ms after it (4K hap q, six hovers, measured by looks at the window that take 34 ms each; 139 to 219 ms before its answer was taken ahead of the controls' pass, in the same sitting), not within the design's 16 to 50 ms; the timebar strip's picture is up meanwhile. the second hardware decoder of an h.264 or hevc clip is open for up to 5 s after it was last asked for something, and is never let go while a clip plays. it keeps no frames behind it, so it asks for 21 fewer surfaces at 4K than the player's own: beside the player's own decoder of a 4K 10-bit hevc clip it adds 94 MB to the program's memory, where with a full pool it added 1170 MB (the pool's 1.1 GB landed there, not on the gpu), and opens in 70 ms where it took 139 (2026-11-24, in a test with no window; an h.264 clip's held about 580 MB of the gpu's before, not measured since). there is no timebar strip on a network volume. it has been looked at only in pictures the window was asked for, not by a person on a real screen, and its key frames have been read from h.264 and x265 hevc made for the tests, not from vp9 nor from files out of cameras or other tools.

### sound

a clip with sound takes its time from the sound, not from the display. the picture keeps the display's even count while the sound is within a frame and a half of it; past that, one frame is held again or passed over, and the title counts it (`resynced`). a 59.94 clip on the 60 Hz display did that twice in 36 s, as the design says it will (about every 17 s); a 60 fps clip did it twice in 10 s, with 2 refreshes late, and a 24 fps clip once in 15 s, with 1 late (2026-11-24, one run each, muted). the player has one way out to the speakers, the system's default output, which every clip's sound goes through in turn; it is opened when sound first plays. a clip's sound is opened with the clip, off the drawing thread.

known gaps:

- **at every start of play, a clip with sound waits for its sound**: the picture holds its frame until the first sound is heard (up to a quarter of a second; not measured). round the end of a looping clip there is no such wait: the sound goes round with the clip, each round cut or made up with silence to the clip's length, begun again from the clip's start. the join is a plain cut in the sound, and has not been listened to (sound has only been run muted here). measured muted on the dev machine, through the seam: a 720p 60 fps h.264 clip went from 24 late refreshes and 17 resyncs to none; a 4K 60 fps h.264 clip at 60 Mbit/s is as it was (none or one late, one to three resyncs over three seams, before and after). where the picture cannot keep up at the seam it now passes frames over to stay with the sound; before, the wait for the sound hid that.
- **the output device is opened on the drawing thread**, once, while the first clip with sound stands still (or at its first play, if it was started at once). that took about 40 ms when every clip opened its own (38 to 43 ms in four runs), and is not measured again. a device that is unplugged or changed while playing is not followed until play starts again. channels beyond stereo are mixed down by ffmpeg's defaults, not the design's table. the metadata panel does not count the repeated frames yet; the title does.

### played folders

the window is sized once, when the headers are read, to the folder's biggest clip, and does not change at a cut. the tab names the folder, the clip's place in it and the clip, as the design's fig. 14 has it (the ink of its letters, arrows and dotted line checked against the figure's at 100%, on the tab that is up). the list under the tab is read from the files' headers in the background (no frame of a video is read; a sequence's first file is decoded for its size); a file that would have to be read through to count its frames shows its size and no more.

the clips before and after the one on screen are kept opened, each with its first frame read, so a cut or a page key only swaps pictures; a clip that is not ready yet is waited for on the last frame of the one before, and the title counts the refreshes that took (`held at cuts`). playing the 19 clips of the 4K and 8K test folder for 30 s made 9 cuts: with each clip opened only when it was reached they held 15 refreshes in all in one run and 9 in another; with the neighbors kept ready, none, and the player held 544 MB against 385 (2026-11-24, one run, cpu at 0 to 1%).

on a network volume each clip is opened only as it plays: no headers are read for the list (it shows names), the clips before and after are not kept ready, and the window is sized to the first clip.

known gap:

- **a played folder is not all the design draws.** on a network volume, which play asks about first, nothing has been tried on a real network share: the asking, the play after it and the watch on an open file were tried only through a share the dev machine serves to itself; and a closed tab that played a folder comes back as its one clip.

### a file that changes on disk

the player holds no lock on what it has open, so a render can write over it. each open file is watched: its size, time and identity a few times a second; on a network volume every two seconds, through its folder's listing asked for that one name, so the file itself is never opened or asked about there, and a look costs the same whatever the folder holds. the whole listing of a folder of 3000 files took 17 to 18 ms a look over a share the dev machine serves to itself, the listing asked for the one name 0.9 ms (2026-11-24). once a changed file has held still for half a second the new file takes the old one's place.

known gap:

- **a sequence is watched by its first file only.** a render that writes over a sequence is picked up when that file changes; frames written after that are read as they are on disk when they are next wanted, and a frame already in memory stays the old one until the clip is opened again.

### stills and sequences

stills and sequences have only been opened as the small files made for the tests. a numbered run opens as one clip from any of its files, on that file's frame, at the rate the file states (exr can) or 24 assumed, and the title says "assumed". a frame with no file is marked amber on the timebar and says so when shown. 8-bit files stay 8-bit, 10, 12 and 16-bit ones go to the screen as 16-bit, and exr as float through the srgb curve with a chip saying so.

### timecode, frame counts and rates

- **timecode is ffmpeg's read of it, and only where ffmpeg reads one.** that is a quicktime timecode track (mov, mp4) or a timecode tag; the design wants our own read of the track in both its forms, and dpx's and mxf's own (mxf does not open at all yet). a 59.94 clip whose track counts 30 names two frames alike, which is not marked. a drop-frame flag on a whole-number rate is not flagged. tested on one file, 29.97 drop-frame; the arithmetic is tested for every frame of two hours.
- **opening an mkv, a webm or a fragmented mp4 reads the whole file first.** they list no frames up front, or not all of them, so the player counts their packets: nothing is decoded, but every packet of the picture is read. it does that off the drawing thread, as it opens every file: what the tab shows stays up meanwhile, and after a quarter of a second a line says `opening name · 12400 frames counted`, the number moving; closing the tab or opening something else stops the count. a file is counted once in a run (it is known after that by its path, size and time), so its sound, its metadata, the timebar's reader and its poster do not count it again. a file is counted only when it is opened to play: its card in the browser stays plain until then, and its metadata there says why it is not read. a 51 MB, 600-frame 4K hevc clip took 23 to 27 ms to count as mkv and 15 to 20 ms as a fragmented mp4, read from the os cache (2026-11-24, release build, three runs each, cpu at 0 to 2%); from a disk or a network share it takes as long as reading the file, which is not measured. a folder holding one of each made the browser read 0.8 MB in all (2026-11-24, one run). ffmpeg has already read the whole table of most fragmented mp4s on opening (all but those with an sidx, whose table stops at the first fragment), but a short table cannot be told from a whole one, so every fragmented mp4 is counted. a mov or mp4 with its table in the moov is not counted. a clip whose frames do not all last the same (a variable rate) is counted too, as its table gives only decode times. other containers without a table (mpeg-ts, for one) still do not play, nor do variable rates outside mov, mp4 and mkv.
- a variable rate plays each frame for its own time, from the refresh nearest its start, and the title says `variable rate`; loop analysis counts its seconds at the clip's average rate. mkv and webm keep time in milliseconds, which cannot hold a 30th of a second, so their rate is derived from the frames' times (the plainest decimal that puts every frame within a millisecond of its time) and says `derived`; a short clip pins it loosely: ten frames of 59.94 read as 60, a minute of them as 59.94 (`times_rounded_to_the_clock_give_a_derived_rate`). the last frame of a variable rate is taken to last as long as the one before it.
- the frame count leaves out what an edit list hides (a clip cut from a longer one without re-encoding), which is tested. pictures that are stored but cannot be decoded are not yet left out, and the counts have only been checked on clips made for the tests, not on files from cameras or other tools.

### color and pixel values

- chroma smaller than the picture (4:2:0, 4:2:2) is blended up from the four samples round each pixel, each where the file sites it, as the design's default has it; `chroma = nearest` in the settings file takes the nearest sample instead, and the metadata panel says which. tested for every pixel of one 4:2:0 h.264 frame against the same arithmetic on the decoder's planes, on both renderers; sitings other than left (center, top left, as hdr hevc has it) are written and have no test clip. where ffmpeg fills in the standard's place for a file that names none, the panel cannot tell and shows it as the file's.
- a file that does not name its color matrix gets the usual assumption (bt.709 at 720 lines and up, bt.601 below). the metadata panel says so, dim; nothing says it on the picture.
- the pixel values in the zoom chip are the red, green and blue the screen is sent, on the scale of the file's bit depth (0 to 255 for 8-bit, 0 to 1023 for 10-bit). they are read from the frame at its own size, not from the window. they are not the stored y'cbcr codes, and they stop at the top of the scale: a hap hdr value above 1.0 reads as the top.

### the metadata panel

- the metadata panel reads timecode through ffmpeg (the design wants our own read of the track), says "not read for this codec yet" for alpha in h.264, hevc and vp9 and for vp9's bit depth, and for stills gives no color facts yet.

### screenshots and markup

- **a screenshot keeps alpha only where the player draws it.** a saved frame keeps the file's alpha for stills, for hap alpha and hap r, and for prores 4444, when the frame has a pixel that is not opaque (an alpha that is opaque all over is left out). hap q alpha is drawn opaque, so its alpha is not saved; hap alpha-only is saved as the gray it is shown as. exr keeps its color multiplied by its alpha, and png wants it not, so a saved exr frame with alpha is too dark where it is partly clear (not handled, and no file of that kind tried). the edges of marks over clear pixels take the hidden color there. the view is saved opaque, 8 or 16 bits by the file's depth; the copy on the clipboard is always 8 bits, and the frame alone.
- **markup is not all the design draws.** a mark is dropped as a click when it is less than 6 of the design's pixels across and down together on screen (the design's prototype counts 6 of the file's pixels, which at 16× would drop a box drawn round one pixel). marks are tested on the test clips, and looked at against the design's figure 19 at the design's size only.
- in markup mode the pointer is a cross where a drag would draw: which pointer the window is told to show is tested; that windows shows it has not been looked at with a real pointer.
- the toast after a save is up for 5 s where others are up for 2.6 s (the design's), and while the pointer is on it, then a second more; its "reveal in explorer" (or finder) is the browser's reveal. the click and the hold are tested in a pass of the controls, not tried by hand in the window yet.
- shift keeps a box square and a circle round in the window's pixels, from where the box's first corner is on screen, so it is square as the picture is shown (turned, mirrored, drawn with square pixels) and not necessarily in the file's. it is read with each press and as it goes down and up, so it can be pressed or let go mid-drag: on windows from its own key messages, on macos from `flagsChanged`, which has not run. tested headless (four ways, a turned picture with pixels drawn wider than high) and in the end-to-end test, which presses it halfway through a drag; not tried with a real keyboard.
- a pen's line is smoothed as it is drawn, and kept as shown: each point the mean of the line round it, the line between the points included, weighted as a bell by how far along it on screen. the bell's sigma is `pen_smoothing` (0 to 1, in the settings file and on settings' screenshots page) times 12 of the design's pixels, 3.6 by default: chosen, not measured against hands. it is taken from the points as the pointer gave them each pass, never from points smoothed before. near the ends the line taken round a point is cut short alike on both sides, so the ends stay where the pointer went down and came up. tested on drawn zig-zags and a wave (the default leaves under 30% of a jitter 1.5 each side, and over 70% of a wave 6 high and 40 long); not tried with a real pointer or pen. boxes, circles and text are not smoothed. the end-to-end test draws no pen stroke.
- a saved frame has the caption, guides and marks as the design's figure 20 draws them on a frame 1200 wide, in proportion to the frame's width, and never smaller than the window shows them at 100%, where a narrow frame's caption runs onto more lines; the view has them as the window shows them.

### the window and tabs

- **a dragged window does not snap to the screen's edges.** the move is the player's own, because the system's move, started from the picture, sometimes did not start. win + arrows, the maximize button and a double click on the strip still arrange the window.
- **tabs keep their clips open.** every tab holds its decoder and the frames it keeps (up to 512 MB each for h.264 and hevc), so many 4K tabs use a lot of memory; nothing is let go until a tab is closed. more tabs than fit the strip narrow to 64 wide, and then the strip scrolls: the tab that comes up is brought into view, and the wheel over the strip moves the tabs.

### the mac release

# needs the mac's screen unlocked (signing uses the login session's keychain) and its ffmpeg from spike/mac/setup.sh,

it writes the mac's notices here (`scripts/notices.ps1 -Target aarch64-apple-darwin`, from a copy of the mac's libavutil), sends the tree, and runs `scripts/mac-bundle.sh` there: `build` over ssh, then `sign` as a launchd job in the login session. a mac does not update itself: its update button opens the release's page.

## package and deploy

```powershell
# tests, release build, dist\eyepiece with the four ffmpeg libraries, their license and the notices, signed as "Tridant, Inc.",
# and the installer of that folder, dist\eyepiece-<version>-windows-setup.exe, signed with its uninstaller
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\package.ps1
# the same, then the folder copied to %LOCALAPPDATA%\Programs\eyepiece
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\package.ps1 -Install
# for a machine without the signing setup: an unsigned folder and installer
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\package.ps1 -NoSign
```

the package step runs the unit tests, the release build and the end-to-end test (a window opens for a few seconds), then copies the program, `avformat-63.dll`, `avcodec-63.dll`, `avutil-61.dll` and `swresample-7.dll`, ffmpeg's license, the two typefaces' licenses and the notices into `dist\eyepiece`, and signs the program and the libraries. last, inno setup 6 (`ISCC.exe`, the only tool the installer needs) compiles `scripts\installer.iss` with the version from Cargo.toml into `dist\eyepiece-<version>-windows-setup.exe` (adr 0008). nothing is deleted: files in dist and in the install folder are overwritten in place.

the installer installs that folder for the user alone, with no admin prompt, into `%LOCALAPPDATA%\Programs\eyepiece`, with a start menu entry and an uninstaller in settings > apps. it asks for one click, on its ready page (inno shows that page whenever no other comes before it), and offers to start eyepiece when it is done. `/VERYSILENT` installs with nothing shown, and `unins000.exe /VERYSILENT` in the install folder takes it all away again, the folder too once it is empty.

signing uses azure artifact signing and needs `AZURE_TENANT_ID`, `AZURE_CLIENT_ID` and `AZURE_CLIENT_SECRET` in the user's environment, the windows sdk's signtool, and microsoft's artifact signing client tools; `-NoSign` skips it, and the installer is then unsigned too. none of their values is printed. inno signs the installer and its uninstaller through the same signtool command, handed to it as a sign tool (`/S`). macOS builds are to be signed on the mac build machine with the developer's signing identity for now; the first public mac build is to carry tridant's own developer id (`docs/design/settings.html`, 11a).

`THIRD-PARTY-NOTICES.txt` in the folder is what the build owes the code of others in it: every crate compiled into the program with its license text, ffmpeg (its version, its source, and how to put other libraries in place of ours) and the two typefaces. `scripts\notices.ps1` writes it from `Cargo.lock`, the crates' own source in the cargo registry and the ffmpeg libraries; the package step runs it, and it runs alone too. `scripts\notices.ps1 -Check` fails, naming the crate, when a crate's license is not on the allow list at the top of the script. today it names ffmpeg-sys-next, which is wtfpl.

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\notices.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\notices.ps1 -Check
```

## releases and updates

a release is cut from the installer with `scripts\release.ps1`. it writes `dist\eyepiece-release.txt`, the release manifest (adr 0007): the version from Cargo.toml, the day, a line for each change in the notes file, and the installer, `dist\eyepiece-<version>-windows-setup.exe`, with its size and sha-256 (adr 0008). with `-Publish` it makes the release `v<version>` on github with `gh`: the installer and the manifest as its assets, and the notes as its text. it refuses first if the installer is not signed. `-Mac` adds the mac's disk image as one more asset, as it is, kept out of the manifest. no library or text file is an asset of a release: they are inside the installer.

```powershell
# the manifest for the installer. notes.md is written as release notes are: a heading for added, changed, fixed; a bullet a change
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\release.ps1 -Notes notes.md
# the same, then the release on github, with the mac's disk image beside it
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\release.ps1 -Notes notes.md -Publish -Mac eyepiece.dmg
```

what the player checks (`src/update`): it reads the manifest of the latest release, `releases/latest/download/eyepiece-release.txt`, and offers only a greater version, compared number by number, whose manifest names its installer. it downloads the installer into `%LOCALAPPDATA%\eyepiece\update\<version>`, checking its size and sha-256 as it lands; one that fails is set aside there as `<name>.failed` (its next failure replaces it), and one already there whole is not downloaded again. before it runs, it is checked again from the disk, and taken only when windows trusts its signature and its signer is the running program's (the certificate's subject and its root; nothing is fetched to decide it). from that check the player holds it open for reading only, starts it with `/SILENT /NORESTART /update=<its pid>` and the files open now in `EYEPIECE_REOPEN`, and closes. the installer waits for that player to end (up to 30 s), installs with its progress on screen, and starts the new build on those files. a build that is not signed itself (a developer build) checks but never updates itself. nothing is sent but the requests, as `eyepiece/<version>`. `EYEPIECE_UPDATE_FROM` (as `http://127.0.0.1:39417/`) reads releases from a folder served by hand, laid out as github's (`latest/download/eyepiece-release.txt`, `download/v<version>/<file>`), with every check as it is; plain http is taken only from 127.0.0.1 (a port outside windows' reserved 8085 to 8184). tried end to end on the dev machine on 2026-11-25, once, with two signed builds: 0.3.0 installed by its installer, very silently, in 5 s; 0.3.1's manifest and installer (40.6 MB) served from 127.0.0.1; update pressed in 0.3.0, open on two clips, by posted messages. 0.3.0 had ended 1.5 s after the press, and 0.3.1's window was up 4.8 s after that, one process, installed byte for byte, on the same two clips (one named with a space and an é). none of it has run against a real github release: the repo is private and adr 0005 holds public downloads. on macOS only the check is written, and it has been neither compiled nor run there.

## the gates (phase 0)

the gate programs live in `spike/`, with their own setup and their own test clips, and are kept until the mac renderer has rerun them.

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File spike\setup.ps1
# makes the test clips in spike\media (about 10 GB with -Big; needs a full ffmpeg on the path for its encoders)
powershell -NoProfile -ExecutionPolicy Bypass -File spike\media.ps1 -Big
powershell -NoProfile -ExecutionPolicy Bypass -File spike\gate.ps1 gate1_zerocopy spike\media\hevc10_4k_5994.mp4
# gate 6 is its own script: a scratch samba share in a small wsl distro (eyepiece-gate6), read from the windows machine or from a mac
powershell -NoProfile -ExecutionPolicy Bypass -File spike\gate6.ps1
```

on windows: `gate1_zerocopy`, `gate2_present`, `gate3_ramp`, `gate4_coldstart`, `gate5_share`, `gate6_browse`, and the measurements `hap_demux`, `hap_speed`, `hap_play`, `decode_speed`, `devtime`. a gate ends with `PASS` or `FAIL`; a measurement only prints numbers.

on macOS (rust and apple's command line tools; the mac build machine has no github access, so `spike/` is copied there with tar over ssh):

```sh
# once: builds an lgpl shared ffmpeg 9.0 with videotoolbox into spike/third_party
sh spike/mac/setup.sh
sh spike/mac/gate.sh gate5_share some-small-clip.mov
# anything that opens a window or needs the keychain runs inside the login session
sh spike/mac/session-run.sh gate2 spike/mac/target/release/gate2_present some-10-bit-hevc.mp4 20
```

there: `gate1_zerocopy`, `gate3_ramp`, `metal_caps`, `gate5_share`, `hap_lane`, `decode_speed` and `vt_check` from any shell; `gate2_present`, `gate4_coldstart`, `hap_play` and `sign-test.sh` (signing and notarization) through `session-run.sh`. what each one found is in `docs/phase-0.md`.
